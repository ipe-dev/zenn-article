## はじめに
B+ツリーの構造はなんとなくわかったけど、何でRDBのインデックスの格納に使われているのかがいまいち理解できませんでした。
そこで今回はB+ツリーの特徴とRDBに使われる理由について調べました。
結論から言うと、B+ツリーは探索のアルゴリズム的にいいのではなく、ディスクからのI/Oをなるべく減らすことができるということです。

## B+ツリーの特徴
B+ツリーはキーとポインタを格納する構造になっています。
リーフノードには実データへのポインタが入っていますが、ルートノードと中間ノードには入っていません。
そのためデータを検索するためには必ずリーフノードまで辿る必要があります。
また1つのノードに入れられる情報量が多いため、ノードからのファンアウト（分岐）も多くなるのが特徴です。

## B+ツリーとRDBのI/O
ここからはPostgreSQLを例に、B+ツリーがいかに効率的にデータのI/Oを行っているか説明します。
これにはRDBがデータを読み取る単位が関係しています。
データを取得する単位はページと呼ばれ、1ページのバイト数はDBMSによって違います。
PostgreSQLの場合は8kBが1ページに割り当てられています。
つまり、読み込む必要があるデータが1バイトだけだったとしても必ず8kBを毎回読み込む必要があるというわけです。

### RDBにおいてはディスクへのI/Oがボトルネックとなる
RDBがデータを読み込む際にはなるべくディスクから読み込まない方が速く処理ができます。
なぜなら、メモリからの読み込みがナノ秒単位なのに対して、SSDはマイクロ秒単位、HDDはミリ秒単位かかるからです。桁が2つずつ違います。
なので、1度ディスクから取得したデータはメモリにキャッシュして次回以降に素早く参照できる仕組みが備わっています。
もう一つの工夫が、読むページ数そのものを減らすインデックスです。
今回のB+ツリーは、このインデックスの情報の保存に使われているデータ構造です。

### 二分木を使った場合
ここでもしインデックスの保存に二分木を使った場合どうなるかを考えます。
二分木の1つのノードには、キー、実データへのポインタ、子ノードへのポインタ2つしか入りません。

二分木のノードの一つひとつの容量は数十バイト程度ですが、RDBでは8kBのページ領域に保存されるため、ページの容量はスカスカな状態で保存されていることになります。
仮に1000万件のデータがあるとすると木の高さは24段になり、検索は24回繰り返す計算になります。
つまりRDBは数十バイト程度のデータを読み取るために8kBのページをディスクから読み取り、該当データがなければまた別のページを読み取り…という作業を繰り返すことになります。

しかも、読み取りを高速化するためにキャッシュしようとしても、8kBのページが1000万件なので約80GBが必要になってしまいます。
これはとてもキャッシュできる量ではありません。

二分木1つのノードで目当てのデータがある場所を1/2までしか絞り込めないために何度もI/Oを発生させる結果となっています。
これはめちゃくちゃ非効率です。

### B+ツリーを使った場合
B+ツリーを使った場合はこの問題を解決しています。
PostgreSQLが読み書きする単位が8kBのページで、B+ツリーのノードはその1枚に収まるように作られています。
すると、ノードの中の情報が無駄なく詰まった状態で取得されます。

ノードの情報を見てみると中間ノードなら283個のエントリが入っています。
1つのノードの情報から必要なデータが入っている範囲を1/283まで絞れることになります。

1000万件のデータがある場合は木の高さが3段になるため、I/Oの回数もノードの読み込み3回＋実データ読み込み1回の合計4回で済みます。

そしてキャッシュも効かせることが可能です。
B+ツリーにおいては99%以上がリーフノードです[^2]。
かつ、木構造なので検索は必ずルートから中間ノードを経由します。
そのため、1%のノードが頻繁に参照され、99%のノードはほぼ参照されないという状況になります。
つまり、1%のノードがキャッシュされていて頻繁にメモリから参照され、99%の中の必要なノードだけがディスクから読み込まれるという仕組みになっているのです[^1]。

## 実測値を見てみる
実際に測定した値を具体的に見てみましょう。

### 環境

- PostgreSQL 17.11（Docker）
- `pgbench -i -s 100` で `pgbench_accounts` を作成（1000万行・1281MB、インデックス214MB）
- 対象インデックスは主キー `pgbench_accounts_pkey`（`btree (aid)`、`aid` は int4）
- 実行計画を単純にするため並列は切って計測（`SET max_parallel_workers_per_gather = 0;`）

### 木の形

```sql
CREATE EXTENSION IF NOT EXISTS pageinspect;

-- 木の高さ（level は「ルートページのレベル」。リーフが 0 なので level=2 は3段）
SELECT * FROM bt_metap('pgbench_accounts_pkey');

-- レベルごとのページ枚数と平均エントリ数
SELECT s.btpo_level AS level, count(*) AS pages, round(avg(s.live_items)) AS avg_items
FROM generate_series(1, (pg_relation_size('pgbench_accounts_pkey')/8192)::int - 1) blk,
     LATERAL bt_page_stats('pgbench_accounts_pkey', blk) s
WHERE s.type <> 'e'
GROUP BY 1 ORDER BY 1 DESC;
```

| level | ページ枚数 | 1ページあたり平均エントリ数 |
| --- | --- | --- |
| 2（ルート） | 1 | 97 |
| 1（中間） | 97 | 283 |
| 0（リーフ） | 27,323 | 367 |

検算：`1 × 97 × 283 ≈ 27,451` ≒ 実測リーフ 27,323枚。`27,323 × 367 ≈ 1003万` ≒ 1000万行。
インデックス全体は 214MB ÷ 8kB ≒ 27,400ページで、そのうち 27,323枚（99.7%）がリーフ。

### 点検索で実際に読んだページ数

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM pgbench_accounts WHERE aid = 4210945;
```

```
 Index Scan using pgbench_accounts_pkey on pgbench_accounts
   (cost=0.43..8.45 rows=1 width=97) (actual time=0.027..0.028 rows=1 loops=1)
   Index Cond: (aid = 4210945)
   Buffers: shared hit=2 read=2
 Execution Time: 0.034 ms
```

合計4ページ。内訳はインデックス3ページ（＝木の高さ）＋テーブル1ページ。

| | 分岐数 | 1000万件での高さ | 点検索で読むページ |
| --- | --- | --- | --- |
| 二分木 | 2 | 24段 | 24枚 |
| B+ツリー（実測） | 283〜367 | 3段 | 3枚（＋テーブル1枚） |

### キャッシュの内訳

同じ木を別のキーで引き直した結果。

```
-- 2回目（同じキー）
WHERE aid = 4210945;  →  Buffers: shared hit=4

-- 別のキー
WHERE aid = 9876543;  →  Buffers: shared hit=2 read=2
```

## まとめ
今回はB+ツリーがいかにデータの検索において最適化されているかをみてきました。
まとめると、

- RDBのI/Oはディスクから読み込まない方が速い
- ノード1つがページ1枚（8kB）に収まるように作られている
- そのぶん分岐を多く取れるので絞り込みが速い（＝木が低くなる）
- 99%のノードは参照される確率が低いからキャッシュされづらく、1%のノードが頻繁に参照されてキャッシュされる

[^1]: 厳密には、一度読まれたリーフもキャッシュに載ります。実測の2回目は `hit=4` で、リーフとテーブルもヒットしています。全クエリが必ず通るルートと中間が、確実に残り続ける2段という意味です。
[^2]: PostgreSQLの公式ドキュメントにも "Typically, over 99% of all pages are leaf pages" と書かれています。[B-Tree Indexes - PostgreSQL Documentation](https://www.postgresql.org/docs/current/btree.html)
